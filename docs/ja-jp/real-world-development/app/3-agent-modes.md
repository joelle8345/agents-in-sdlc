最初はプロジェクトに小さな機能を追加しましたが、より大きな変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに合わせて作業できるため、適切なものを適切な方法で構築できます。このレッスンから、issue を使った新機能の作成、コードと動作の確認、最終的なマージという、エージェント主導の一般的な開発プロセスに取り組みます。

> [!NOTE]
> 機能の作業を続ける間は、同じセッションを使います。通常はファイル種別ごとに別のセッションやプルリクエスト (PR) を作成しますが、ここでは主要な概念に集中するため手順を簡略化しています。

このレッスンでは、次の内容を行います。

- GitHub issue から新しいエージェントセッションを開始する。
- **Plan** モードで要件を定義する。
- **Autopilot** モードで新機能を実装する。
- コードをレビューする。
- ブラウザーキャンバスで機能を手動検証する。

この機能の作業を続ける中で、リポジトリの instruction を更新し、既存の quality-checks スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが拡大し、訪問者がカテゴリとパブリッシャーでゲームを絞り込める必要があります。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意しておきたい詳細があります。Plan モードで決定し、範囲を定めた実装を Autopilot に許可します。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細が記載された issue を開く。
2. 構築する内容の計画を作成する。
3. コードを構築してレビューする。
4. テストを実行してコードを検証する。
5. 新機能を手動で検証する。
6. プルリクエスト (PR) を作成する。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージする。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを基本とします。

この標準的なアプローチに従うことで、AI が生成したコードが要件を満たし、手書きのコードと同じ確認プロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントに与える自律性の度合いを制御します。プロンプトフィールドの下にあるドロップダウンで設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが共同で作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律して作業し、入力を待たずにコードの作成、テストの実行、反復を行います。

まず Plan モードで計画を確認し、その後 Autopilot で実装します。

## issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。既存の **Allow users to filter games by category and publisher** を開きます。この issue はテンプレートで用意されているため、別の issue を作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` の実行を依頼します。ターミナルでは成功しセッション内で失敗する場合は、アプリの PATH またはバージョン管理ツールの設定を確認してから、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルタリング機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。issue から開始したため、Copilot は機能のリクエストをコンテキストとしてすでに持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を issue の受け入れ条件と照らし合わせます。カテゴリとパブリッシャーによるフィルタリング、アクセシブルなコントロール、データアクセスの変更、テストが計画に含まれていることを確認します。複数カテゴリの組み合わせ方や、一致するゲームがない場合の動作など、不明確な点について話し合います。

計画には、プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。フィルタリングの実装とテストに集中し、品質ワークフローを終えてから PR を作成します。計画を承認する前に必要な修正を依頼し、後で検証できるよう issue の URL と合意した詳細を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで同等のオプションを選択します。承認によってモードが切り替わると思い込まず、モード表示が **Autopilot** になっていることを確認します。

Copilot は実装に取りかかり、合意した計画に沿ってコードを生成し、テストを実行しながら作業を反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードも、ほかのコードと同じように、マージ前にレビューします。コードを確認し、サイトを実行して問題がないことを確かめます。

1. **Changes** を開き、フィルタリングの実装とテストを確認します。
2. 複数カテゴリとパブリッシャーの組み合わせも含め、結果を issue と承認した追加の決定事項に照らし合わせます。変更が既存のリポジトリ instruction に従っていることも確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、影響するチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカルサーバーを再利用する場合があります。テスト対象が以前のレッスンではなく、現在の worktree に属するサーバーであることを確認してください。

## 新機能を確認する

コードに問題がなさそうでも、実際に動くことを確認します。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使って、アプリを起動しブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選択し、結果がそのカテゴリに一致することを確認します。フィルターを解除し、パブリッシャーを選んで結果が一致することを確認します。
4. カテゴリとパブリッシャーのフィルターを組み合わせ、issue と承認済みの計画に合った結果になることを確認します。複数カテゴリに対応する場合は、合意した組み合わせ方をテストします。
5. 一致するゲームがない条件を試し、結果が空の場合の表示を確認します。フィルターを解除またはリセットして、一覧全体が戻ることを確認します。
6. 終了したら、次のプロンプトでこのセッションの開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けてセッションを保持する

フィルタリングの PR はまだ作成またはマージしないでください。レッスン 4 から 8 まで、同じセッション、worktree、ブランチを使います。次はカスタム instruction をフィルタリングのコードに適用し、スキルと QA の改善を加えてから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後はセッションをそのままにし、次のレッスンで再開してください。

## まとめと次のステップ

異なるエージェントモードを使って機能を構築し、レビューしました。このレッスンでは、次の作業を行いました。

- GitHub issue から新しいエージェントセッションを開始した。
- **Plan** モードで要件を定義した。
- **Autopilot** モードで新機能を実装した。
- コードをレビューした。
- ブラウザーキャンバスで機能を手動検証した。
